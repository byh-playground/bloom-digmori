# 디그모리 게임 기획 (재정리 초안)

기준 커밋: main 5f8d1b8 · 제품 0.28.14 · GameKit 고정 `418e17c`(v0.14.3, 최신 v0.37.0 계열은 1단계에서 교체)

이 문서는 규칙 AI-001·002·004·005·008·012의 순서(의도 → 조사 → 동작 확정 → 구현)를 따른 기획 원본이다. 수치와 단계 이름은 **초안(가설)** 이며, 수직 슬라이스를 직접 플레이해 재미를 확인한 뒤 확정한다. 확정되기 전의 내용을 확정 사양으로 취급하지 않는다(AI-002).

## 1. 근거 구분 (AI-004)

| 구분 | 내용 |

| 사용자 요구 (확정) | 복셀 월드 + 빌보드 캐릭터 렌더 유지. 수동으로 시작해 점점 자동화. 획득한 유닛으로 전투. 렌더 교체. GameKit 최신화. **멀티(락스텝 결정론)는 처음부터 전제. 시뮬레이션은 구조적으로 부동소수를 쓰지 않는다**. 기존 아트·렌더는 모킹용이라 버리고, 컨셉 → 아트 → 모듈·렌더 일괄 개선 순서로 진행. **마크식 성장(자원 → 장비 → 보스 → 다음 단계), 진행 축은 한 월드 안의 바이옴(포탈 없음), 단계는 장비 페널티로 구분, 이전 바이옴 자원이 이후에도 필요**. 인디게임(스팀) 수준을 목표로 하되 적은 리소스로 재미를 낸다 |

| 이번 초안 | 아래 2~6절 전체 |
| 미확인 | 서로 다른 브라우저·OS 조합의 실제 비트 일치(현재 검증은 동일 PC 2인 RTC까지). Palworld 세부 수치는 2차 가이드 위주라 설계 근거로만 쓴다. Dome Keeper·Core Keeper의 판매 수치는 퍼블리셔 발표 중심이고 두 게임의 아트 예산은 확인하지 못했다 |

## 2. 한 문장

> 자원을 모아 장비를 만들고 보스를 쓰러뜨려 다음 바이옴으로 가며, 이전 바이옴의 자원도 계속 필요하기 때문에 내 손으로 하던 수급을 점점 자동화해 더 먼 곳으로 간다.

## 3. 성장 구조와 자동화

### 3.0 확정한 방향 (사용자 결정)

| 항목 | 결정 | 이유 |
|---|---|---|
| 성장 방식 | 마크식: 자원 수집 → 장비 제작 → 보스 처치 → 다음 단계. 한 세계에서 오래 성장 | 짧은 런(로그라이트)이 아니라 장기 성장을 원함 |
| 진행 축 | 수평 **바이옴** | 깊이 기반은 수평은 무한한데 수직 단계는 수십 m라 스케일이 어긋남 |
| 월드 구조 | **한 월드 안에 바이옴이 놓인다**(마크식). 포탈은 쓰지 않는다 | 클릭 데모에서 포탈은 탭 전환일 뿐 이동 비용이 없어 순환 자원 요구가 부담이 되지 않았다. 한 월드면 거리가 곧 비용이다 |
| 단계 구분 | 바이옴 입장은 자유. **장비를 못 갖추면 큰 페널티**를 받는다(막지 않는다) | 문이 아니라 준비도로 단계가 나뉜다 |
| 바이옴 간 관계 | 이전 바이옴의 자원이 이후에도 필요하도록 설계해 바이옴이 서로 맞물림 | 한 번 지나가면 끝나는 직선 진행을 피하고, 지역이 낭비되지 않게 모든 바이옴을 반복해서 오가게 함 |
| 전투 | 내가 조작 + 유닛 지원 | 기존 결정 유지 |

**폐기한 방향:** 깊이 축, 거리 링 축, 포탈로 연결한 별도 바이옴, 적성·작업장·분업 체인(Palworld와 너무 비슷함). 이유는 기록으로만 남긴다.

**멀티 영향:** 공간이 하나라서 "서로 다른 바이옴을 같이 갱신"하는 문제가 없어졌다. 기존 플레이어 주변 활성 영역 방식을 그대로 쓴다.

### 3.1 장비 페널티 (확정한 원칙 + 데모에서 시험한 초안 수치)

원칙: 장비 없이도 들어갈 수 있지만 얻는 것이 크게 줄거나 잃는 것이 크게 는다. 그래서 장비를 맞추는 것이 진행의 단계가 된다.

| 바이옴(예시) | 위험 | 장비 | 장비 없을 때 페널티 (초안) |
|---|---|---|---|
| 초원 | 없음 | 돌 도끼 | 보스전: 공격 1/4, 받는 피해 4배 |
| 동굴 | 어둠 | 철 곡괭이 | 채굴이 4배 느림, 보스전 페널티 |
| 균류 숲 | 포자 독 | 포자 갑옷 | 체력이 계속 깎임, 보스전 페널티 |

클릭 데모(1회용 목업, 저장소에는 남기지 않음)에서 보스 HP 20, 장비 있음 공격 4 / 없음 1, 받는 피해 초당 2 / 8, 균류 독 초당 2로 시험했다. 이 수치는 가설이며 슬라이스 플레이 후 조정한다(AI-008: 장비 유무 배율 4를 기준으로 파생).

### 3.2 제안 (미확정)

아래는 확정 사항에서 파생한 **제안**이다. 사용자 확인 전에는 사양으로 취급하지 않는다(AI-002).

**① 순환 자원 요구가 자동화의 동기가 된다.** 바이옴 N의 장비 레시피에 이전 바이옴의 자원이 하나씩 들어간다. 처음에는 걸어서 오가며 직접 모으지만 바이옴이 깊어질수록 이동 비용이 커진다. 그때 이전 바이옴의 수급을 유닛에게 넘기는 것이 "수동 → 자동화"다.

**② 보스가 동료로 합류한다.** 보스를 쓰러뜨리면 그 보스가 거점의 동료가 되고, 보스의 테마가 그 유닛의 역할이 된다. 유닛은 바이옴 수(약 6)만큼이라 역할을 하나씩 직접 설계할 수 있다. 전투에 보내면 노동에서 빠진다.

**③ 월드는 유한한 반경.** 거점을 중심으로 걸어서 몇 분 안에 닿는 반경에 바이옴 조각을 시드로 배치한다. 무한 월드에 거리로 단계를 늘어놓으면 한 방향으로만 가서 지역이 낭비되기 때문이다. 무한 확장은 후속으로 미룬다.

```text
        [동굴 · 어둠]
            │
[초원] ─ [거점] ─ [균류 숲 · 포자 독]     ← 거점에서 걸어서 수 분 거리, 바이옴 조각은 시드로 배치
```

**④ 에셋 규모 추정 (가설).** 바이옴당 타일 6~8종, 일반 적 2~3종, 보스 1종, 장비 아이콘 몇 개. 6단계 합계가 대략 타일 40종·적 15종·보스 6종·아이콘 수십 개다. 실제 제작 시간은 아트 단계에서 실측한다.

### 정상·반례 사례 (AI-005)

- 정상: 초원에서 나무·돌로 돌 도끼를 만든다 → 뿌리 거인을 쓰러뜨려 동료로 합류시킨다 → 동굴에서 철을 캔다 → 철 곡괭이에 초원의 나무가 필요해 돌아가거나, 동료가 모아 둔 것을 쓴다 → 철 곡괭이로 동굴 채굴이 빨라지고 보스에 도전한다.
- 반례 1: 장비 없이 동굴에 들어가면 입장은 되지만 채굴이 4배 느리다. 무엇이 부족한지 표시한다.
- 반례 2: 장비 없이 균류 숲에 오래 머물면 체력이 깎여 쓰러지고 거점에서 깨어난다. 보스는 회복한다.
- 반례 3: 제작은 거점에서만 가능하다. 자원을 들고 돌아오는 이동이 실제 비용이다(가방과 보관함의 구분은 §7).
- 반례 4: 멀티에서 한 명은 동굴, 다른 한 명은 초원에 있다. 한 월드이므로 기존 활성 영역 방식으로 둘 다 같은 틱에 갱신된다.
- 반례 5: 플레이어 주변 활성 영역 밖의 자동 수급을 어떻게 성립시킬지는 §7.

### 수치 초안 (AI-008)

미정이다. 수동 채집 1회를 기준값 1.0으로 두고 동료 수급 속도를 배율(0.5)로 파생하는 원칙만 유지한다. 장비 페널티 배율은 3.1을 따른다.

## 4. 아트·렌더링 요구

기존 아트·렌더러는 초기 모킹용이라 재사용하지 않고 버린다. 아트는 §3 컨셉(한 월드의 바이옴, 장비 페널티, 보스)이 읽히도록 새로 뽑는다. 바이옴은 타일만 보고도 구분돼야 하고, 위험(어둠·포자 독 등)은 화면에서 바로 보여야 하며, 보스와 동료는 테마(역할)가 실루엣으로 읽혀야 한다.

- 복셀 월드: 청크 메시 + 면별 음영·AO로 입체감, 거리 안개.
- 캐릭터: 빌보드. 아트 형식(SVG 메시 + 스케치·털실 머티리얼 / 픽셀 스프라이트)은 아트 단계에서 정한다(§7).
- 표현은 시뮬레이션 상태를 **읽기만** 한다. 렌더·VFX가 자원·피해·위치를 만들지 않는다.

## 5. 결정론·락스텝 계약 (처음부터의 전제)

**원칙: 시뮬레이션 상태와 그 갱신식에는 부동소수가 없다.** 결정론을 "부동소수가 대체로 같게 나온다"에 맡기지 않고, 같은 정수 입력이 같은 정수 결과를 내는 구조로 만든다. 부동소수는 표현(렌더·UI·VFX)에서만 쓰고, 시뮬레이션이 표현의 값을 읽지 않는다.

현재 확인한 사실(as-is): 락스텝(`profiles.lockstep`, 30 TPS)과 주기적 체크섬이 있고 동일 PC 2인 RTC에서 공통 틱 해시가 일치했다. 그러나 시뮬레이션이 `rapier3d-deterministic-compat 0.21.0`(float) 위에 있고(`world.step`·`castRay`·`setLinvel` 등 약 30개 호출처), 위치·속도·피해 계산이 `CFG`의 소수(m 단위)다. 이 구조는 위 원칙에 맞지 않으므로 교체 대상이다.

규칙:

1. **수 표현:** 위치·속도·거리·시간은 정수 고정소수(Q10: 1 m = 1024 단위, GameKit `deterministic.fixedPoint`)나 정수 틱으로 둔다. int32 범위를 매 연산에서 검증한다. 소수 상수는 설정 로드 시 한 번 `fromNumber`로 변환하며, 갱신식에는 쓰지 않는다.
2. **물리:** 복셀 월드는 격자라서 충돌을 정수로 풀 수 있다. 플레이어·동료·투사체는 고정소수 AABB와 복셀 충돌(축별 이동 후 해소)로 직접 구현한다. Rapier는 시뮬레이션에서 제거한다. 투척체 포물선도 정수 중력 가산으로 만든다.
3. **수학:** 제곱근·삼각함수·`atan2`는 쓰지 않는다. 거리 비교는 제곱 거리, 방향은 정수 벡터/방향 테이블, 길이는 정수 제곱근(뉴턴법)을 쓴다. GameKit `fixedPoint`에는 덧셈·뺄셈·곱셈·나눗셈만 있어 제곱근과 방향 테이블은 **공통 모듈 개선 대상**이다(AI-009: 최소 재현 후 GameKit에 추가 → 버전 반영 → 게임 적용).
4. **시간·난수:** 시뮬레이션은 틱의 함수다. 시각·`Date.now`·프레임 dt를 쓰지 않는다. 난수는 시드 PRNG(`SeededPRNG`)만 쓰고 상태를 스냅샷에 포함한다.
5. **자동화:** 동료 노동은 격자 칸·정수 좌표·틱 카운터의 이산 상태기계다. 물리 바디를 두지 않는다. 경로 탐색은 틱당 예산을 두고 라운드 로빈으로 분산한다(AI-012).
6. **경로 단일화:** 단독 플레이도 1인 락스텝 세션이다. 입력은 인코딩된 명령으로만 시뮬레이션에 들어간다.
7. **소유권:** 개체·작업 칸·보관함의 생성/수정 주체는 `Simulation` 한 곳이다(DEV-001). 다른 참가자 소유 개체 명령은 거부하고, 공유 칸 충돌은 틱 순서·참가자 ID 순으로 판정한다.
8. **표현 보간:** 렌더는 시뮬레이션의 정수 상태를 읽어 float로 보간한다. 역방향(렌더 값 → 시뮬레이션)은 없다.
9. **검증:** 슬라이스마다 ① 같은 시드·입력 두 번 실행 시 체크섬 일치, ② 2인 RTC에서 체인 구동 중 공통 틱 해시 일치, ③ 저장 → 복원 후 같은 입력의 같은 결과, ④ 시뮬레이션 소스에서 `Math.sin|cos|atan2|sqrt|random`·`Date.now`·소수 리터럴 사용을 정적 검사로 막는다. 서로 다른 브라우저·OS 간 실제 비교는 별도 검증 범위로 기록한다(미확인).

### 이 원칙이 바꾸는 것 (as-is → to-be)

```text
as-is: Rapier(float) 월드 ── step ──▶ 위치/속도(float, m) ──▶ 체크섬
       노동 동료 = Rapier 바디
to-be: 정수 AABB ── 복셀 충돌(정수 축 해소) ──▶ 위치/속도(Q10 int32) ──▶ 체크섬
       노동 동료 = 격자 상태기계(바디 없음)
       렌더 = 정수 상태 → float 보간 (읽기 전용)
```

저장 호환: 기존 float 저장은 이 전환에서 호환하지 않는다. 게임은 미배포이므로 Breaking 부담이 없다.

## 6. 단계별 계획

순서: 컨셉 → 아트 → 모듈·렌더·정수 코어 일괄 개선 → 슬라이스. 아트가 먼저 나와야 모듈·렌더 개선의 목표 화면이 정해진다.

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| 0 | 이 문서: 컨셉(§3.0) 확정 | PR 머지. 수치·단계는 가설로 명시 |
| 1 | 아트 뽑기: 바이옴 타일, 위험 표현, 보스·동료, 장비 아이콘 모킹 | 사용자가 컨셉이 읽힌다고 확인 (같은 장면 캡처 비교) |
| 2 | 모듈·렌더·정수 코어 일괄: GameKit 최신화, 렌더러 교체, `fixedPoint` 보강, 복셀 AABB 물리, Rapier 제거, 정적 검사 | 기존 이동·채굴·점프·수영·전투 재현, 같은 입력 체크섬 일치, 2인 RTC 해시 일치, 임시 렌더러 삭제 |
| 3 | 수직 슬라이스: 바이옴 2개 + 거점·이동 + 장비 페널티 + 보스 1마리 + 순환 자원 요구 1개 | §3 정상·반례 사례를 E2E로 재현, 결정론 검증 4종 |
| 4 | 바이옴·보스·유닛 확장, 자동 수급 체인 | 슬라이스 플레이 후 재미 판단을 근거로 범위 확정 |

3단계에서 "재미없음"이 관찰되면 §3을 수정하며 코드보다 문서를 먼저 고친다.

## 7. 열린 질문

- 보스 보상: 보스가 동료로 합류하는 안(3.2 ②)을 쓸지, 재료만 주는 안을 쓸지.
- 월드 반경과 바이옴 조각 배치 방식(3.2 ③): 걸어서 몇 분이 적당한지, 시드 배치 규칙.
- 페널티 강도(3.1): 배율 4가 적당한지, 장비 없이 도전하는 플레이를 어디까지 허용할지.
- 가방과 거점 보관함의 구분: 들고 다니는 한도, 동료가 모은 자원의 운반 방식(데모는 거점에 바로 쌓이도록 단순화함).
- 플레이어 주변 활성 영역 밖의 자동 수급을 어떻게 성립시킬지(로드 중에만 진행 / 방문 시 경과 틱 일괄 계산). 결정론과 맞아야 한다.
- 바이옴 수, 사망 규칙(현재 데모: 거점에서 깨어남), 아트 형식(SVG 메시 + 스케치·털실 머티리얼 / 픽셀 스프라이트 시트).
- 정수 물리로 바꿀 때 현재 이동 감각(자동 오르기, 수영, 구르기)을 어디까지 재현할지: 2단계 착수 시 같은 시나리오 전후 비교로 정한다.
- 서로 다른 OS·브라우저 간 실제 일치 비교 방법과 시점.
