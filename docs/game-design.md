# 디그모리 게임 기획 (재정리 초안)

기준 커밋: main 5f8d1b8 · 제품 0.28.14 · GameKit 고정 `418e17c`(v0.14.3, 최신 v0.37.0 계열은 1단계에서 교체)

이 문서는 규칙 AI-001·002·004·005·008·012의 순서(의도 → 조사 → 동작 확정 → 구현)를 따른 기획 원본이다. 수치와 단계 이름은 **초안(가설)** 이며, 수직 슬라이스를 직접 플레이해 재미를 확인한 뒤 확정한다. 확정되기 전의 내용을 확정 사양으로 취급하지 않는다(AI-002).

## 1. 근거 구분 (AI-004)

| 구분 | 내용 |
|---|---|
| 사용자 요구 (확정) | 복셀 월드 + 빌보드 캐릭터 렌더 유지. 수동으로 시작해 점점 자동화. 획득한 유닛으로 전투. 렌더 교체. GameKit 최신화. **멀티(락스텝 결정론)는 처음부터 전제. 시뮬레이션은 구조적으로 부동소수를 쓰지 않는다**. 기존 아트·렌더는 모킹용이라 버리고, 컨셉 → 아트 → 모듈·렌더 일괄 개선 순서로 진행 |
| 조사로 확인 | ① Factorio 개발진은 수동 채굴 → 자동 채굴 → 자동 물류 → 자동 생산 순서를 진행의 핵심 축으로 둔다. 각 단계가 *직전까지 손으로 하던 일*을 대체하므로 업그레이드가 값져 보인다 ([FFF-327](https://factorio.com/blog/post/fff-327)). ② Palworld는 개체마다 작업 적성이 있고 적성 등급이 높을수록 작업이 효율적이다. 거점은 통나무·채석처럼 단순한 생산에서 시작해 자동 제작으로 간다는 안내가 많다. 월드가 로드된 동안만 일하고, 먹이·휴식이 필요하다 ([Mobalytics](https://mobalytics.gg/gamebase/guides/palworld-base-pal-guide), [HostedGG](https://hostedgg.com/blog/palworld-base-building-guide)). ③ Rapier JS 빌드는 같은 빌드·같은 timestep에서 교차 플랫폼 결정론을 주장하지만 내부는 부동소수이고, `Math.sin/cos` 같은 초월함수는 플랫폼마다 다를 수 있다([Rapier 결정론](https://rapier.rs/docs/user_guides/javascript/determinism)). 이 게임은 결정론을 라이브러리의 보증에 맡기지 않고 **시뮬레이션 상태를 정수·고정소수로 둔다**(사용자 확정, §5) |
| 이번 초안 | 아래 2~6절 전체 |
| 미확인 | 서로 다른 브라우저·OS 조합의 실제 비트 일치(현재 검증은 동일 PC 2인 RTC까지). Palworld 세부 수치는 2차 가이드 위주라 설계 근거로만 쓴다 |

## 2. 한 문장

> 처음엔 내 손으로 캐고 만들다가, 내가 하던 일을 하나씩 동료에게 넘기고, 풀려난 손과 시간으로 더 먼 곳을 탐험·전투해 다시 더 큰 일을 맡긴다.

## 3. 유닛 역할과 자동화 (컨셉 확정 + 단계 초안)

### 3.0 확정한 컨셉 (사용자 결정)

| 질문 | 결정 | 의미 |
|---|---|---|
| 유닛이 무슨 일을 하는가 | **적성 레벨** | 모든 유닛이 작업 종류별 적성 레벨을 가진다. 같은 종도 개체마다 다르다. 작업장에 배치하면 그 작업의 적성 레벨이 속도를 정한다 |
| 일을 넘기는 방법 | **거점 설비 배치** | 거점에 작업장(벌목장·채석장 등)을 짓고 유닛을 배치한다. 일은 작업장 반경 안에서만 한다 |
| 자원이 거치는 길 | **분업 체인** | 채집 유닛 → 운반 유닛 → 가공 유닛이 이어진다. 운반이 없으면 채집이 멈추고, 가공이 느리면 운반이 쌓인다. 병목을 찾아 유닛을 교체·증원하는 것이 재미 |
| 전투 | **내가 조작 + 유닛 지원** | 플레이어가 직접 싸우고 유닛 슬롯의 기술을 쓴다. 전투에 보낸 유닛은 노동에서 빠진다 |

```text
[채집 적성3] 통나무 ─▶ [운반 적성3] ─▶ [가공 적성2] 판자 ─▶ 내 보관함
   벌목장 반경 안            작업장 → 가공장           가공장

유닛 = { 개체ID, 종, 적성{채집, 운반, 가공, ...}, 위치: reserve | work | combat }
```

작업 종류의 목록(채집·운반·가공 외 무엇이 있는지)과 적성 레벨의 범위는 아직 정하지 않았다(§7).

### 3.1 자동화 사다리 (초안)

각 단계는 "직전까지 내가 손으로 하던 일 하나"를 대체한다. 대체되는 일이 없는 자동화는 넣지 않는다.

| 단계 | 내가 손으로 하던 일 | 넘기는 방법 (해금) | 풀려나는 것 → 새 목표 |
|---|---|---|---|
| A0 수동 | 채굴·채집·제작·운반 전부 | 시작 | 도구·작업대, 첫 유닛 포획 |
| A1 채집 위임 | 흙·나무·풀 등 기초 자원 채집 | 작업장 1곳 + 채집 적성 유닛 1마리. 이 단계에서는 채집한 유닛이 보관함까지 직접 나른다(운반 분업 전) | 광석·동굴 탐험 |
| A2 운반 분업 | 채집물을 보관함으로 옮기기 | 운반 적성 유닛이 작업장과 보관함을 잇는다. 채집 유닛은 채집만 한다 | 제작에 집중, 거점 확장 |
| A3 가공 분업 | 제련·제작 반복 | 가공장 + 가공 적성 유닛. 채집 → 운반 → 가공 체인 완성 | 던전·보스, 상위 유닛 포획 |
| A4 병목 최적화 | 어떤 유닛을 어디에 둘지 | 체인의 병목 표시, 적성 높은 개체 교체·증원 | 전투 슬롯과 노동 배치의 **유닛 경쟁** |

전투 유닛과 노동 유닛은 같은 개체 풀이다. 한 개체는 노동·전투·보관 중 한 곳에만 있다(현재 `reserve | work | combat` 구조 유지). "일을 시킬지, 싸우게 할지"가 핵심 선택이다.

### 정상·반례 사례 (AI-005)

- 정상: 수동 채집 중 첫 동료를 포획 → 거점 채집 배치 → 자리를 비워도 보관함이 찬다 → 돌아와 수령하고 그 시간에 동굴을 탐험한다.
- 반례 1: 보관함이 가득 차면 동료는 운반 물품을 쥔 채 정지하고 이유를 표시한다(기존 계약 유지).
- 반례 2: 전투 슬롯으로 불러낸 동료는 노동에서 빠지고, 노동 쪽에 빈자리가 생긴 사실이 거점에 표시된다.
- 반례 3: 같은 거점에서 두 참가자가 같은 자원 칸에 작업을 걸면 한 명만 성립한다(§5 소유권).
- 반례 3-1: 체인 중간(운반) 유닛이 전투로 빠지면 앞 단계가 막히고, 어느 단계가 왜 멈췄는지 작업장에 표시한다.
- 반례 4: 플레이어가 거점에서 멀어 월드가 로드되지 않은 동안은 진행하지 않는다(Palworld와 같은 제약, 오프라인 보상은 만들지 않는다).

### 수치 초안 (AI-008: 기준값 1개에서 배율 파생)

- 기준값 `수동 채집 1회 = 1.0`. 유닛 작업 속도 = 해당 작업의 적성 레벨 × `0.5` (예: 레벨 1·2·3 → `0.5 / 1 / 1.5`). 레벨 범위는 §7에서 정한다.
- 운반 용량·보관함 칸 수는 기존 값(9칸, 스택 한도)을 유지한다. 재정규화는 요청 시에만 한다.
- 위 수치는 슬라이스 플레이 후 조정 대상이다.

## 4. 아트·렌더링 요구

기존 아트·렌더러는 초기 모킹용이라 재사용하지 않고 버린다. 아트는 §3 컨셉(적성·작업장·분업 체인)이 읽히도록 새로 뽑는다. 유닛은 종과 **적성**이 한눈에 구분돼야 하고, 작업장은 어떤 일을 하는지와 막힌 이유가 보여야 한다.

- 복셀 월드: 청크 메시 + 면별 음영·AO로 입체감, 거리 안개.
- 캐릭터: 빌보드. 아트 형식(SVG 메시 + 스케치·털실 머티리얼 / 픽셀 스프라이트)은 아트 단계에서 정한다(§7).
- 표현은 시뮬레이션 상태를 **읽기만** 한다. 렌더·VFX가 자원·피해·위치를 만들지 않는다.

## 5. 결정론·락스텝 계약 (처음부터의 전제)

**원칙: 시뮬레이션 상태와 그 갱신식에는 부동소수가 없다.** 결정론을 "부동소수가 대체로 같게 나온다"에 맡기지 않고, 같은 정수 입력이 같은 정수 결과를 내는 구조로 만든다. 부동소수는 표현(렌더·UI·VFX)에서만 쓰고, 시뮬레이션이 표현의 값을 읽지 않는다.

현재 확인한 사실(as-is): 락스텝(`profiles.lockstep`, 30 TPS)과 주기적 체크섬이 있고 동일 PC 2인 RTC에서 공통 틱 해시가 일치했다. 그러나 시뮬레이션이 `rapier3d-deterministic-compat 0.21.0`(float) 위에 있고(`world.step`·`castRay`·`setLinvel` 등 약 30개 호출처), 위치·속도·피해 계산이 `CFG`의 소수(m 단위)다. 이 구조는 위 원칙에 맞지 않으므로 교체 대상이다.

규칙:

1. **수 표현:** 위치·속도·거리·시간은 정수 고정소수(Q10: 1 m = 1024 단위, GameKit `deterministic.fixedPoint`)나 정수 틱으로 둔다. int32 범위를 매 연산에서 검증한다. 소수 상수는 설정 로드 시 한 번 `fromNumber`로 변환하며, 갱신식에는 쓰지 않는다.
2. **물리:** 복셀 월드는 격자라서 충돌을 정수로 풀 수 있다. 플레이어·동료·투사체는 고정소수 AABB와 복셀 충돌(축별 이동 후 해소)로 직접 구현한다. Rapier는 시뮬레이션에서 제거한다. 투척체 포물선도 정수 중력 가산으로 만든다.
3. **수학:** 제곱근·삼각함수·`atan2`는 쓰지 않는다. 거리 비교는 제곱 거리, 방향은 정수 벡터/방향 테이블, 길이는 정수 제곱근(뉴턴법)을 쓴다. GameKit `fixedPoint`에는 덧셈·뺄셈·곱셈·나눗셈만 있어 제곱근과 방향 테이블은 **공통 모듈 개선 대상**이다(AI-009: 최소 재현 후 GameKit에 추가 → 버전 반영 → 게임 적용).
4. **시간·난수:** 시뮬레이션은 틱의 함수다. 시각·`Date.now`·프레임 dt를 쓰지 않는다. 난수는 시드 PRNG(`SeededPRNG`)만 쓰고 상태를 스냅샷에 포함한다.
5. **자동화:** 동료 노동은 격자 칸·정수 좌표·틱 카운터의 이산 상태기계다. 물리 바디를 두지 않는다. 경로 탐색은 틱당 예산을 두고 라운드 로빈으로 분산한다(AI-012).
6. **경로 단일화:** 단독 플레이도 1인 락스텝 세션이다. 입력은 인코딩된 명령으로만 시뮬레이션에 들어간다.
7. **소유권:** 개체·작업 칸·보관함의 생성/수정 주체는 `Simulation` 한 곳이다(DEV-001). 다른 참가자 소유 개체 명령은 거부하고, 공유 칸 충돌은 틱 순서·참가자 ID 순으로 판정한다.
8. **표현 보간:** 렌더는 시뮬레이션의 정수 상태를 읽어 float로 보간한다. 역방향(렌더 값 → 시뮬레이션)은 없다.
9. **검증:** 슬라이스마다 ① 같은 시드·입력 두 번 실행 시 체크섬 일치, ② 2인 RTC에서 체인 구동 중 공통 틱 해시 일치, ③ 저장 → 복원 후 같은 입력의 같은 결과, ④ 시뮬레이션 소스에서 `Math.sin|cos|atan2|sqrt|random`·`Date.now`·소수 리터럴 사용을 정적 검사로 막는다. 서로 다른 브라우저·OS 간 실제 비교는 별도 검증 범위로 기록한다(미확인).

### 이 원칙이 바꾸는 것 (as-is → to-be)

```text
as-is: Rapier(float) 월드 ── step ──▶ 위치/속도(float, m) ──▶ 체크섬
       노동 동료 = Rapier 바디
to-be: 정수 AABB ── 복셀 충돌(정수 축 해소) ──▶ 위치/속도(Q10 int32) ──▶ 체크섬
       노동 동료 = 격자 상태기계(바디 없음)
       렌더 = 정수 상태 → float 보간 (읽기 전용)
```

저장 호환: 기존 float 저장은 이 전환에서 호환하지 않는다. 게임은 미배포이므로 Breaking 부담이 없다.

## 6. 단계별 계획

순서: 컨셉 → 아트 → 모듈·렌더·정수 코어 일괄 개선 → 슬라이스. 아트가 먼저 나와야 모듈·렌더 개선의 목표 화면이 정해진다.

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| 0 | 이 문서: 컨셉(§3.0) 확정 | PR 머지. 수치·단계는 가설로 명시 |
| 1 | 아트 뽑기: 유닛 종·적성 표현, 작업장, 복셀 월드 타일 모킹 | 사용자가 컨셉이 읽힌다고 확인 (같은 장면 캡처 비교) |
| 2 | 모듈·렌더·정수 코어 일괄: GameKit 최신화, 렌더러 교체, `fixedPoint` 보강, 복셀 AABB 물리, Rapier 제거, 정적 검사 | 기존 이동·채굴·점프·수영·전투 재현, 같은 입력 체크섬 일치, 2인 RTC 해시 일치, 임시 렌더러 삭제 |
| 3 | 수직 슬라이스 A0~A2: 적성 데이터, 작업장, 채집·운반 체인, 노동 상태기계 | §3 사례를 E2E로 재현, 결정론 검증 4종 |
| 4 | A3·A4, 전투 슬롯과 노동 배치의 경쟁, 던전 보상 연결 | 슬라이스 플레이 후 재미 판단을 근거로 범위 확정 |

3단계에서 "재미없음"이 관찰되면 §3을 수정하며 코드보다 문서를 먼저 고친다.

## 7. 열린 질문
