# 디그모리 게임 기획 (재정리 초안)

기준 커밋: main 5f8d1b8 · 제품 0.28.14 · GameKit 고정 `418e17c`(v0.14.3, 최신 v0.37.0 계열은 1단계에서 교체)

이 문서는 규칙 AI-001·002·004·005·008·012의 순서(의도 → 조사 → 동작 확정 → 구현)를 따른 기획 원본이다. 수치와 단계 이름은 **초안(가설)** 이며, 수직 슬라이스를 직접 플레이해 재미를 확인한 뒤 확정한다. 확정되기 전의 내용을 확정 사양으로 취급하지 않는다(AI-002).

## 1. 근거 구분 (AI-004)

| 구분 | 내용 |
|---|---|
| 사용자 요구 (확정) | 복셀 월드 + 빌보드 캐릭터 렌더 유지. 수동으로 시작해 점점 자동화. 획득한 유닛으로 전투. 렌더 교체. GameKit 최신화. **멀티(락스텝 결정론)는 처음부터 전제** |
| 조사로 확인 | ① Factorio 개발진은 수동 채굴 → 자동 채굴 → 자동 물류 → 자동 생산 순서를 진행의 핵심 축으로 둔다. 각 단계가 *직전까지 손으로 하던 일*을 대체하므로 업그레이드가 값져 보인다 ([FFF-327](https://factorio.com/blog/post/fff-327)). ② Palworld는 개체마다 작업 적성이 있고 적성 등급이 높을수록 작업이 효율적이다. 거점은 통나무·채석처럼 단순한 생산에서 시작해 자동 제작으로 간다는 안내가 많다. 월드가 로드된 동안만 일하고, 먹이·휴식이 필요하다 ([Mobalytics](https://mobalytics.gg/gamebase/guides/palworld-base-pal-guide), [HostedGG](https://hostedgg.com/blog/palworld-base-building-guide)). ③ Rapier JS 빌드는 교차 플랫폼 결정론이고 월드 스냅샷 해시로 기기 간 비교가 가능하다. 단 `Math.sin/cos` 같은 초월함수는 플랫폼마다 다를 수 있어 초기 조건에도 쓰면 안 된다([Rapier 결정론](https://rapier.rs/docs/user_guides/javascript/determinism)) |
| 이번 초안 | 아래 2~6절 전체 |
| 미확인 | 서로 다른 브라우저·OS 조합의 실제 비트 일치(현재 검증은 동일 PC 2인 RTC까지). Palworld 세부 수치는 2차 가이드 위주라 설계 근거로만 쓴다 |

## 2. 한 문장

> 처음엔 내 손으로 캐고 만들다가, 내가 하던 일을 하나씩 동료에게 넘기고, 풀려난 손과 시간으로 더 먼 곳을 탐험·전투해 다시 더 큰 일을 맡긴다.

## 3. 핵심 루프와 자동화 사다리 (초안)

각 단계는 "직전까지 내가 손으로 하던 일 하나"를 대체한다. 대체되는 일이 없는 자동화는 넣지 않는다.

| 단계 | 내가 손으로 하던 일 | 넘기는 방법 (해금) | 풀려나는 것 → 새 목표 |
|---|---|---|---|
| A0 수동 | 채굴·채집·제작·운반 전부 | 시작 | 도구·작업대, 첫 동료 포획 |
| A1 채집 위임 | 흙·나무·풀 등 기초 자원 채집 | 동료 1마리를 *한 작업*에 배치 (속도는 수동의 `1/2`) | 광석·동굴 탐험 |
| A2 운반 위임 | 채집물을 보관함으로 옮기기 | 보관함·운반 작업 적성 동료 | 제작에 집중, 거점 확장 |
| A3 가공 위임 | 제련·제작 반복 | 제작 설비 + 설비 담당 동료 (채집 → 운반 → 가공 체인) | 던전·보스, 상위 동료 포획 |
| A4 편성 최적화 | 어떤 동료를 어디에 둘지 | 적성·성격(속도 배율)·휴식 규칙 | 전투 편성과 노동 편성의 **자원 경쟁** |

전투 동료와 노동 동료는 같은 개체 풀이다. 한 개체는 노동·전투·보관 중 한 곳에만 있다(현재 `reserve | work | combat` 구조 유지). 이것이 "일을 시킬지, 싸우게 할지"의 핵심 선택이다.

### 정상·반례 사례 (AI-005)

- 정상: 수동 채집 중 첫 동료를 포획 → 거점 채집 배치 → 자리를 비워도 보관함이 찬다 → 돌아와 수령하고 그 시간에 동굴을 탐험한다.
- 반례 1: 보관함이 가득 차면 동료는 운반 물품을 쥔 채 정지하고 이유를 표시한다(기존 계약 유지).
- 반례 2: 전투 슬롯으로 불러낸 동료는 노동에서 빠지고, 노동 쪽에 빈자리가 생긴 사실이 거점에 표시된다.
- 반례 3: 같은 거점에서 두 참가자가 같은 자원 칸에 작업을 걸면 한 명만 성립한다(§5 소유권).
- 반례 4: 플레이어가 거점에서 멀어 월드가 로드되지 않은 동안은 진행하지 않는다(Palworld와 같은 제약, 오프라인 보상은 만들지 않는다).

### 수치 초안 (AI-008: 기준값 1개에서 배율 파생)

- 기준값 `수동 채집 1회 = 1.0`. 동료 채집 속도 = 적성 등급 × `0.5`(A1) → 등급별 `0.5 / 1 / 1.5`.
- 운반 용량·보관함 칸 수는 기존 값(9칸, 스택 한도)을 유지한다. 재정규화는 요청 시에만 한다.
- 위 수치는 슬라이스 플레이 후 조정 대상이다.

## 4. 렌더링 요구 (상세는 1단계 문서에서)

- 복셀 월드: 청크 메시 + 면별 음영·AO로 입체감, 거리 안개. 월드 메시는 GameKit `rendering`의 mesh 경로를 쓴다.
- 캐릭터: 원본 SVG(Pages에 바이트 단위 배포) → 시작 시 1회 컴파일·캐시 → 빌보드 메시/스프라이트 애니메이션(AI-010). 빌드로 굽지 않는다.
- 표현은 시뮬레이션 상태를 **읽기만** 한다. 렌더·VFX가 자원·피해·위치를 만들지 않는다(현 계약 유지).

## 5. 결정론·락스텝 계약 (처음부터의 전제)

현재 확인한 사실: 락스텝(`profiles.lockstep`, 30 TPS), `rapier3d-deterministic-compat 0.21.0`, 주기적 체크섬이 이미 있다. 동일 PC 2인 RTC에서 공통 틱 해시 일치를 확인했다. 시뮬레이션 코드의 `performance.now()`는 프로파일링 계측이고 `Math.random()`은 렌더러에만 있다.

새 기획이 지켜야 할 규칙:

1. **시뮬레이션 상태는 틱의 함수다.** 시각·`Date.now`·`performance.now`·프레임 dt를 시뮬레이션 결과에 쓰지 않는다(계측 제외).
2. **난수는 시드 PRNG만** 쓴다. 상태(`prngState`)는 스냅샷에 포함한다. 포획·드롭·전투 확률 모두 해당한다.
3. **자동화는 물리 바디가 아닌 이산 상태기계**로 만든다(초안). 동료 노동을 격자 칸·정수 좌표·틱 카운터로 표현하면 동료가 늘어도 Rapier 비용이 늘지 않고, 부동소수 불일치 위험 면적도 준다. Rapier는 플레이어와 전투 투사체·충돌에만 쓴다. 현재 구현은 노동 물리체가 Rapier 월드에 있으므로 2단계에서 교체 대상이다.
4. **시뮬레이션 안에서 `Math.sin/cos/atan2`를 쓰지 않는다.** 필요하면 테이블 또는 GameKit `fixedPoint`를 쓴다. 표현 계층에서는 허용한다.
5. **모든 참가자가 같은 코드 경로**를 지난다. 단독 플레이도 1인 락스텝 세션이다. 입력은 인코딩된 명령으로만 시뮬레이션에 들어간다.
6. **소유권:** 개체·작업 칸·보관함의 생성/수정 주체는 `Simulation` 한 곳이다(DEV-001). 다른 참가자 소유 개체에 대한 명령은 거부한다. 공유 자원 칸은 틱 순서·참가자 ID 순으로 결정론적으로 판정한다.
7. **반복 계산은 틱 예산 안에서:** 동료 N마리 × 경로·탐색은 틱당 상한과 라운드 로빈으로 분산한다(AI-012). 비용은 실측한다.
8. **검증:** 매 슬라이스마다 ① 같은 시드·입력 두 번 실행 시 체크섬 일치, ② 2인 RTC에서 자동화 체인 구동 중 공통 틱 해시 일치, ③ 스냅샷 저장 → 복원 후 같은 입력에서 같은 결과. 서로 다른 브라우저/OS 조합은 별도 검증 범위로 기록한다(미확인).
